# Stand-in

A **stand-in** is an agent that answers another agent's questions in your place, inside that agent's own conversation. You give it a brief — who it is and what it wants — and it plays that person: the coding agent asks "which database?", the stand-in answers "Postgres, keep it simple", and the work continues without you.

The two roles, in the terms users tend to reach for:

| Role         | What it is                                                                      |
| ------------ | ------------------------------------------------------------------------------- |
| **Agent**    | The normal Paseo agent session doing the work. Nothing about it changes.        |
| **Stand-in** | An internal agent that reads the agent's messages and replies as the requester. |

The stand-in's replies land in the agent's normal timeline as ordinary prompts, so the whole exchange reads as one conversation in one tab. That is the point: you can open the agent later and read what was decided.

## Where it sits

Paseo already had three ways to push work into an agent without you typing. Stand-in is the fourth, and the only one that reacts to what the agent actually said:

| Feature       | Trigger                | Content                            | Target            |
| ------------- | ---------------------- | ---------------------------------- | ----------------- |
| **Schedule**  | Cron                   | Fixed prompt                       | A brand new agent |
| **Heartbeat** | Cron                   | Fixed prompt                       | The same agent    |
| **Loop**      | Previous run ended     | The same prompt, again             | A fresh worker    |
| **Stand-in**  | The agent's turn ended | Generated by an LLM from the brief | The same agent    |

## How a turn works

```
agent finishes a turn (running → idle)
        │
        ▼
read the agent's last assistant message
        │
        ├─ same message as last time, or a run is in flight → do nothing
        │
        ▼
ask the stand-in agent for a decision (schema-validated JSON)
        │
        ├─ "done"  → stand-in completes; nobody is prompted
        └─ "reply" → send the reply into the agent's conversation
```

The stand-in agent is a normal internal Paseo agent (`internal: true`, so it stays out of the sidebar) with its own persistent session. The brief is sent once, on the first exchange; after that it keeps its own memory of the conversation.

Starting a stand-in on an agent that is **already idle** picks up its current message immediately. That is the common case: you read a question the agent asked, decide you would rather not babysit it, and hand it to a stand-in.

## Using it

```bash
# Start
paseo standin start <agent> "You are the product owner for the billing rewrite.
You want it shipped behind a flag today. Prefer boring, well-tested choices.
Approve refactors only if they are needed for the flag."

# Watch the conversation
paseo standin logs <stand-in-id>

# List / inspect / stop
paseo standin ls
paseo standin inspect <stand-in-id>
paseo standin stop <stand-in-id>
```

`<agent>` accepts a full agent ID, a unique ID prefix, or an exact title — the same identifier resolution as `paseo send`.

### Run the agent in a mode that does not need you

This is the difference between a stand-in that works and one that stalls. A stand-in answers **messages**; it does not answer **permission prompts**. An agent in an ask-first mode will get its question answered, start working, hit the first `Write`, and stop — waiting for a human who by definition is not there. The stand-in logs that and waits until it runs out of time.

Start the agent in a mode where it can act on its own (`--mode bypassPermissions` or `acceptEdits` for Claude; the equivalent per provider), and the exchange runs to completion. Verified end to end: agent asks for the heading → stand-in answers → agent writes the file → stand-in answers `done`.

Useful flags on `start`:

| Flag                 | Effect                                                                    |
| -------------------- | ------------------------------------------------------------------------- |
| `--provider/--model` | Which provider and model the stand-in itself runs on (defaults to Claude) |
| `--name <name>`      | Names the stand-in, and by default becomes the reply label                |
| `--label <text>`     | Prefix added to every reply (defaults to the name, or `Stand-in`)         |
| `--no-label`         | Send replies verbatim, with no prefix                                     |
| `--max-replies <n>`  | Stop after this many replies (default 20)                                 |
| `--max-time <dur>`   | Stop after this much wall-clock time                                      |
| `--archive`          | Archive the stand-in agent when the stand-in ends instead of closing it   |

### The reply label

Replies are prefixed with `[Stand-in] ` by default. This is deliberate: a chat where you cannot tell your own words from a machine's is worse than a slightly noisy one. `--no-label` turns it off when the agent's behavior depends on the prompt reading naturally.

## Writing a brief

The brief is the whole feature. It is a persona plus a goal, not a task description — the agent already has the task.

Good:

> You are the on-call engineer who filed this bug. You care that the fix is minimal and lands today. You know the payment code well and will push back on refactors. If asked about rollout, say behind the `billing_v2` flag.

Weak:

> Answer the agent's questions.

The stand-in is instructed to be concrete: pick an option, state a preference, approve or reject, and never punt with "do whatever you think is best" unless the brief says so. A vague brief produces a stand-in that agrees with everything, which is how an agent ends up confidently building the wrong thing.

## Stopping

A stand-in ends when:

| Status      | Cause                                                                        |
| ----------- | ---------------------------------------------------------------------------- |
| `completed` | The stand-in decided the brief was satisfied                                 |
| `stopped`   | `paseo standin stop`, or the agent's session closed                          |
| `failed`    | Hit `--max-replies` / `--max-time`, the agent errored, or the stand-in broke |

One agent can have at most one running stand-in. Starting a second one is an error, not a silent replacement.

Stand-ins do **not** survive a daemon restart: on startup, a `running` record is recovered as `stopped` with a log entry. The stand-in's own session state is a live conversation the daemon was mediating, and resuming half of it would produce replies to a turn nobody remembers.

## Limits in this version

- **Permission requests are not answered.** If the agent asks to run a tool, or asks a question through a provider permission prompt (Claude's `AskUserQuestion`), the stand-in logs that a human is needed and waits. It never approves a tool call. Answering `kind: "question"` permissions means constructing provider-specific `updatedInput`, which is deliberately out of scope here; approving `kind: "tool"` permissions is a different decision entirely and should stay a human one. In practice this is why the agent's mode matters — see above.
- **No UI.** Stand-ins are started and read from the CLI. The replies themselves are visible in the normal agent tab, because they are normal prompts.
- **No MCP tool.** An agent cannot yet spawn a stand-in for another agent.
- **Everyone shares the channel.** If you type into the same agent while a stand-in is running, both of you are talking to it. The stand-in reacts to the agent's next message either way.

## Storage

```
$PASEO_HOME/standins/standins.json
```

One file holding every stand-in record, written atomically through an in-memory queue. See [data-model.md](data-model.md#6-stand-in) for the record shape.
